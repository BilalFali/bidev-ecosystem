You're starting a Flutter project and the state management decision is blocking everything else. Every tutorial picks a different one, every "it depends" answer tells you nothing, and you need to commit before you write a single screen. Here's how to actually decide, based on what each one costs you in practice, not just what it promises in its README.

The issue-count gap is the number worth sitting with. flutter_bloc has 85 open issues against a package that's been API-stable for over a year. GetX has 1,184 against a last repo push several months back. That's not proof GetX is abandoned, it still has an active publisher and a 5.0 release candidate on pub.dev, but it's a real signal that reported problems are piling up faster than they're closed. If you're choosing for a project that needs to still be maintainable in two years, that ratio matters more than like counts.

## Riverpod: when compile-time safety is worth the setup cost

Riverpod's actual pitch isn't "better Provider", it's that your app won't compile if you access a provider that doesn't exist, forget to dispose something, or read state outside the right scope. That category of bug just doesn't happen.

```dart
@riverpod
class CartTotal extends _$CartTotal {
  @override
  double build() {
    final items = ref.watch(cartItemsProvider);
    return items.fold(0.0, (sum, item) => sum + item.price);
  }
}
```

The cost: you're running code generation (`build_runner`) for the modern `@riverpod` annotation style. If your team is allergic to generated files or your CI pipeline is already slow, that's friction on every single PR. The older `Provider`/`StateNotifierProvider` syntax still works without codegen, but you lose some of the ergonomics that make Riverpod worth choosing over plain Provider in the first place.

**Pick Riverpod when:** you want strong testability and compile-time guarantees, your team can tolerate a codegen step, and you're building something that will have multiple contributors over a long timeline.

**Wrong choice when:** it's a small app with one maintainer and a tight deadline. The setup overhead isn't worth it for a weekend project.

## BLoC: when you want state transitions you can actually prove are correct

BLoC's whole design is: every state change is an explicit, named event mapped to an explicit, named state. There's no ambiguity about how you got from state A to state B, because the event that caused it has a name and you can test it in isolation.

```dart
sealed class CartEvent {}
class ItemAdded extends CartEvent { final Item item; ItemAdded(this.item); }

class CartBloc extends Bloc<CartEvent, CartState> {
  CartBloc() : super(CartState.initial()) {
    on<ItemAdded>((event, emit) {
      emit(state.copyWith(items: [...state.items, event.item]));
    });
  }
}
```

That explicitness is also the complaint everyone has about BLoC: for a screen with three fields and a submit button, you're writing an event class, a state class, and a bloc class before you've touched a single widget. It's verbose by design, not by accident, that's the trade for traceability.

**Pick BLoC when:** the app has complex, multi-step state transitions you need to test thoroughly (checkout flows, multi-stage forms, anything finance or healthcare adjacent), or you're working on a team where "what triggered this state change" needs to be obvious to someone who didn't write it.

**Wrong choice when:** the screen's state logic is genuinely simple. Writing a full event/state/bloc trio for a toggle switch is boilerplate for its own sake.

## GetX: when shipping speed matters more than long-term structure

GetX's appeal is real: reactive variables with `.obs`, a built-in router, dependency injection, snackbars and dialogs, all without a `BuildContext` in sight. You can build a functional app faster in GetX than in either alternative.

```dart
class CartController extends GetxController {
  final items = <Item>[].obs;
  double get total => items.fold(0.0, (sum, item) => sum + item.price);
  void addItem(Item item) => items.add(item);
}
```

The documented, widely-discussed downside: GetX leans on a global service-locator pattern (`Get.find()`) instead of Flutter's own dependency graph, which makes controllers harder to mock cleanly in unit tests and makes it easy to accidentally leak state between routes if you're not careful about controller lifecycle (`Get.put` vs `Get.lazyPut` vs permanent bindings). None of that is a verified bug, it's an architectural trade-off: less structure means less safety net.

**Pick GetX when:** you're building an MVP, prototype, or small-to-medium app solo and shipping speed beats long-term test coverage.

**Wrong choice when:** multiple developers will touch the codebase, or the app's complexity is going to grow for years. The lack of enforced structure that helps you move fast early becomes the thing slowing you down later.

## Common mistake across all three

Picking based on GitHub stars or "what my bootcamp taught" instead of your project's actual shape. A solo prototype doesn't need BLoC's ceremony. A five-person team building a banking app shouldn't be reaching for GetX's convenience. The library isn't the hard part, matching it to your project's complexity and team size is.

## The actual recommendation

If you have to pick one default for a new mid-to-large app with more than one contributor: Riverpod, for the compile-time safety and testability, and because the codegen friction is a one-time setup cost, not a recurring one. Reach for BLoC specifically when state transitions need to be provably correct and testable in isolation. Use GetX only when you've already decided speed matters more than structure for this specific project, not as a default.
